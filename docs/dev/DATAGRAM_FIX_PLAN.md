# DATAGRAM 开启后异常的成因分析与修复方案

> 结论先行：**不是单点 bug，是三个设计缺口叠加**。
> 关闭即正常、开启即出问题，说明问题全部集中在 DATAGRAM 这条支路上。
>
> 本文只谈分析与方案，不含实现。

---

## 1. 现象与实测数据

### 1.1 关闭 DATAGRAM（正常）

```
nslookup www.google.com 1.1.1.1
  → 一次成功，无超时
```

### 1.2 开启 DATAGRAM（异常）

```
DNS request timed out.  timeout was 2 seconds.     ← 丢
DNS request timed out.  timeout was 2 seconds.     ← 又丢
非权威应答:
名称: www.google.com
Addresses: 142.251.155.119 ...                    ← 第三次才成
（AAAA 记录全部缺失 —— IPv6 查询超时被放弃）
```

一次解析要等 **4~6 秒**。

### 1.3 历史数据（同类问题）

| 场景 | 观测 |
|---|---|
| 3.4~3.6（流连接未开 DATAGRAM） | 客户端 `path_udp_sent=N`、`path_udp_recv=0`；日志 `datagram support disabled` |
| FEC 开启（节点无解码） | 节点 `丢弃无法解析的报文 len=332`，网页全断 |
| 单连接 + 回退上线后 | 节点 `DATAGRAM 流量 tx` 增长、`dropped=0`，但客户端仍收不到 |
| 关闭 DATAGRAM | 一切正常，DNS 秒回 |

---

## 2. 成因分析

### 缺口 A：DATAGRAM 天生不可靠，而我们把 DNS 放了上去

QUIC DATAGRAM（RFC 9221）的语义就是**不重传、不排序**。

实测这条路径的丢包率约 0.4~0.6%（QUIC 层 `quic_lost` 观测）。对可靠流，这
0.4% 由 QUIC 重传吃掉，用户无感；对 DATAGRAM，这 0.4% 就是**直接丢失**。

DNS 客户端（Windows resolver）的超时是 2 秒，于是：

```
查询丢一次 → 等 2 秒 → 重试
应答丢一次 → 等 2 秒 → 重试
两个方向各丢一次 → 4~6 秒
```

这不是我们代码的 bug，是**把不可靠通道用在了最怕丢的流量上**。

### 缺口 B：FEC 只实现了客户端一半

M4 实现了 XOR 分组 FEC，但只在客户端：

| 位置 | 现状 |
|---|---|
| 客户端发送 | 编码 `[type][group][index][IP]` |
| 客户端接收 | 解码 + 还原 |
| **节点接收** | **无解码** —— 把 4 字节 FEC 头当 IP 头解析，判坏包丢弃 |
| **节点发送** | **无编码** —— 下行根本没有冗余 |

实测证据：节点日志 `丢弃无法解析的报文 len=332`（332 = 4 字节 FEC 头 + 328 字节 IP 报文）。

所以「开启 FEC」= 上行 UDP 100% 被丢 = 网页全断。这是**能力缺失**，不是参数问题。

### 缺口 C：分流粒度太粗（按协议号一刀切）

现在是：

```
TCP(6)  → 可靠流
UDP(17) → DATAGRAM（全部）
ICMP(1) → 可靠流
```

但 UDP 内部的可靠性需求差异极大：

| 流量 | 能否容忍丢包 |
|---|---|
| DNS（UDP 53） | **完全不能** —— 丢了就是用户等 2 秒 |
| QUIC / HTTP3 网页 | 能（自带重传） |
| 视频通话 | 能（丢帧好过卡顿） |
| 游戏 | 能（丢位置比延迟好） |

把 DNS 和游戏放同一条不可靠通道，是这次问题最直接的来源。

### 缺口 D：没有能力协商

面板开关只改一个布尔值，两端实际能力完全没对齐过：

- 客户端不知道节点是否支持 FEC 帧
- 节点不知道客户端是否真的在读 DATAGRAM
- 开关打开后，任一侧能力缺失都表现为「静默丢包」

前面三次事故（FEC 全断、关开关反而断、下行归零）全部源于此。

## 3. 修复方案

分四步，**每一步都必须能独立验证、独立回退**。

### 阶段 0（已做）：止血

```
datagram_enabled = false
fec_mode         = off
```

全部 UDP 走可靠流，DNS 秒回。**这是当前唯一稳定配置。**

### 阶段 1：FEC 变成两端共用能力

| 项 | 内容 |
|---|---|
| 抽包 | 把 `vpnclient/fec.go` 抽到共享包（如 `internal/fecns`），客户端与节点都 import |
| 节点解码 | `readSession` 先过 FEC 解码，还原后才交给 `StripPadding` |
| 节点编码 | 下行 `tunLoop → DATAGRAM` 前做 FEC 编码，按同样的 group/index 规则 |
| 单测 | 复用现有 `fec_test.go`，另加「节点收到 FEC 帧能还原」用例 |

验收：面板 `fec_mode=xor` 开启后，`path_udp_recv > 0` 且 DNS 不再出现 2 秒超时。

### 阶段 2：能力协商（让开关不再"盲开"）

```
客户端 → POST /tunnel 请求头：X-VPN-Datagram: 1; fec=xor; k=8
节点   → 响应头：X-VPN-Datagram: ok; fec=xor; k=8
```

- 节点不认 FEC → 回 `fec=off`，客户端**自动降级为不编码**，绝不发节点解不了的帧
- 客户端未声明 → 节点按纯 DATAGRAM 处理（兼容旧客户端）
- 面板开关只在两端协商成功后生效，否则面板显示「节点不支持」

验收：人为把节点版本降级，客户端应自动退回纯可靠流而不丢包。

### 阶段 3：按流量特征分流（关键）

把「按协议号」细化为「按用途」：

| 流量 | 通道 | 理由 |
|---|---|---|
| **DNS（UDP 53）** | **可靠流** | 最怕丢，2 秒超时对用户是灾难 |
| 其他 UDP 小包（< 512B） | DATAGRAM + FEC | 实时性优先，丢了有 FEC 兜 |
| 大 UDP（如 QUIC 传输大文件） | 可靠流 | 吞吐优先，HoL 影响小 |
| TCP / ICMP | 可靠流 | 不变 |

判断依据：目的端口 53 直接判可靠流；其余按包长决定。

验收：
- `nslookup` 在任何开关状态下都必须一次成功、无超时
- 大流量下载时 DNS P95 不退化

### 阶段 4（可选）：DATAGRAM 上的轻量 ARQ

如果阶段 1~3 之后 DATAGRAM 的实际丢包仍影响体感，再考虑：

- 在 DATAGRAM 上对「必须送达的少量包」做应用层确认 + 重传（本质是把可靠流的选择性重传搬到 DATAGRAM）
- 复杂度高，优先级最低；**先用阶段 3 的「DNS 走可靠流」就能覆盖绝大多数痛点**

---

## 4. 验收标准总表

| 指标 | 通过条件 |
|---|---|
| DNS（开启 DATAGRAM） | 一次成功，无 `timeout was 2 seconds` |
| `path_udp_sent` vs 节点 `DATAGRAM tx` | 差距 ≤ 1% |
| `path_udp_recv` | > 0，且与节点 `DATAGRAM rx` 同量级 |
| 节点 `dropped` | 保持 0 |
| 网页可访问 | 任何开关状态下都能打开 |
| 回退 | 面板一键切回纯可靠流，无需发版 |

---

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 抽共享包后客户端/节点版本不匹配 | 阶段 2 的能力协商兜底：不认就降级 |
| FEC 开销（1/K）影响带宽 | K 默认 8（12.5%），且只作用于 UDP |
| 分流规则写错导致 DNS 又被丢进去 | 单测覆盖「目的端口 53 → stream」这条硬规则 |
| 再次出现「下行归零」 | 已有 tunLoop 的通道回退；再加「下行 5 秒无包」告警日志 |

---

## 6. 明确不做

| 项 | 原因 |
|---|---|
| 让 DATAGRAM 自己变可靠 | QUIC 规范如此，改写等于自己实现一套传输层 |
| 用 FEC 覆盖 TCP | TCP 由流负责重传，FEC 救不了拥塞窗口 |
| 保留「UDP 全走 DATAGRAM」的粗粒度分流 | 正是本次问题的根源 |

---

## 7. 当前建议

**保持关闭**，直到阶段 1~3 完成。

理由：
- 开启后能拿到的收益（小包不被队头阻塞）在 FEC 补齐前根本拿不到
- 代价却是 DNS 从「秒回」变成「等 4~6 秒」
- 这个开关已经引发过三次「网页全断」，风险远大于收益

如果希望降低误开风险，可考虑**暂时隐藏面板开关**（保留配置项与后端能力），
等阶段 3 完成后再放出。
