# 隧道加速方案（参考 Hysteria2）

> 目标：解决两个实测问题 —— 带宽偏小、大流量下会误判/抖动。
> 本文只谈方案与取舍，不含实现。

---

## 1. Hysteria2 到底用了什么

把 hy2 的加速手段逐项拆开，标明「能不能搬到我们这里」。

| hy2 的手段 | 原理 | 我们能搬吗 |
|---|---|---|
| **BBR 拥塞控制** | 用带宽×RTT 估计代替丢包退让，跨境高延迟链路上比 CUBIC 快数倍 | ✅ 能，但要换 quic-go 分支 |
| **Brutal（自研）** | 两端协商固定带宽，按该速率发包，**丢包也不降速** | ⚠️ 需要拥塞控制钩子，上游 quic-go 不开放 |
| **QUIC 原生多路复用** | 每条 TCP 连接一条 QUIC 流，丢包只阻塞那一条 | ✅ 能，但要改成分片多流（我们是 L3） |
| **UDP 走 QUIC DATAGRAM** | UDP 本身不需要有序，丢了就丢 | ✅ 能，收益中等 |
| **Socket 缓冲放大** | BDP = 带宽 × RTT，默认 64KB 缓冲会把吞吐锁死 | ✅ 能，改动最小、收益最直接 |
| Salamander 混淆 / 端口跳跃 | 抗封锁，与速度无关 | — |

### 关键认知：hy2 是 L4，我们是 L3

hy2 代理的是 TCP 连接，所以「一条连接一条流」天然成立。
我们承载的是 **IP 包**，没有连接概念，所以「多路复用」在我们这里必须换成
**按五元组哈希分片到 N 条流** —— 保证同一条 TCP 连接始终落在同一条流上，
顺序不乱；不同连接分散到不同流，一条流丢包只影响它上面那部分流量。

### 关于「丢包补偿」

hy2 并没有做前向纠错（FEC）。它的「丢包补偿」本质是 **Brutal 忽略丢包**：
认为用户配置的带宽就是链路真实容量，丢包是链路拥塞而非容量不足，于是照速发。

在应用层做 FEC 在我们这里没有意义：丢包是 QUIC 检测的，
QUIC 会重传，应用层补出来的包救不了拥塞窗口。

## 2. 我们现在的瓶颈

```
客户端 TUN → pumpUp → SendPacket(拷贝) → 队列 → writeLoop → io.Pipe
     → HTTP/3 单流（CUBIC，150ms RTT）
     → 节点 readStream → TUN → 内核转发 → 公网
```

已确认/已解决：

- 双重分帧（2.17 修）
- Wintun 封装层截断（2.35 修，直连 ring API）
- 节点上行 syscall/分配（2.38 优化：bufio + 缓冲复用）
- 大流量下误判不通（2.38 修）

仍然存在的结构性上限：

| 上限 | 影响 | 量级 |
|---|---|---|
| **单条可靠流** | 任何丢包 → 整条流队头阻塞 | 丢 1% 可掉一半吞吐 |
| **CUBIC** | 一丢包就砍窗口，150ms RTT 下恢复极慢 | 跨境链路损失最大的一项 |
| **UDP socket 缓冲** | 默认 64KB，BDP 需要 ~2MB | 可能直接锁死在几十 Mbps |
| 每包多次拷贝 | 高 pps 下 CPU/GC 抖动 | 次要 |

> BDP 估算：100 Mbps × 150 ms ≈ **1.9 MB**。
> 若 socket 接收缓冲只有 64KB，理论吞吐上限约 `64KB / 0.15s ≈ 3.4 Mbps`。
> 这一项必须先量再改 —— 很可能就是「带宽偏小」的主因。

## 3. 分三期落地

### 一期：把「不该丢的吞吐」拿回来（低成本，1~2 天）

| 项 | 做法 | 预期 |
|---|---|---|
| **放大 UDP socket 缓冲** | 自建 `net.UDPConn` 并 `SetReadBuffer/SetWriteBuffer(4MB)`，再用 `quic.Transport{Conn: ...}` 接管；客户端 `http3.Transport.Dial` 里复用该 conn | 若当前受限于此，吞吐可翻数倍 |
| **PMTU 探测兜底** | 节点与客户端统一 `DisablePathMTUDiscovery` + 固定 MTU（管理端已可配） | 消除偶发黑洞 |
| **客户端零拷贝上行** | `SendPacket` 改成 `sync.Pool` 取缓冲，writeLoop 归还 | 降低 GC 停顿 |
| **节点下行缓冲池** | `sess.send` 同样用池 | 同上 |

一期不改协议，风险低，先量出「缓冲放大后能到多少」，再决定要不要上多流。

### 二期：多流分片（中等，3~5 天）

这是我们能拿到的「hy2 多路复用」等价物。

**协议改动**

```
客户端并行开 N 条 POST /tunnel（N=4，可配）
每条流带同一个 JWT，请求头加 X-VPN-Shard: i/N
节点：同一 device 允许 N 条并发流，注册成同一个 session 的 N 个 shard
```

**分流规则**

```
shard = fnv32a(五元组) % N
五元组 = (源IP, 目的IP, 协议, 源端口, 目的端口)
```

- 同一条 TCP/UDP 流始终同一条 shard → 顺序不变
- 不同流分散 → 丢包只阻塞 1/N 的流量

**收益**：丢包 1~2% 时，HoL 阻塞影响从「全量」降到「约 1/N」。
配合 CUBIC，实际吞吐通常能提升 50%~150%。

**风险**：流数不是越多越好。4 条是常见甜点；8 条以上会放大 QUIC 头部开销
和调度抖动，弱网下反而更差。

### 三期：换拥塞控制（大改，5~8 天 + 长期维护）

这是 hy2 真正的速度来源，也是唯一能根治「跨境高延迟 + 丢包」的手段。

**方案 A：换成 apernet/quic-go 分支（推荐）**

- Hysteria2 用的就是 `github.com/apernet/quic-go`，它在 `quic.Config` 里
  暴露了 `CongestionControl`，可选 BBR
- 改动：客户端与节点同时换 import，验证 API 兼容（该分支跟随上游，
  但版本可能落后）
- 收益：跨境链路上 BBR 相对 CUBIC 常见 2~4 倍
- 风险：多一个第三方分支持久维护；API 漂移要跟

**方案 B：自建 Brutal 式固定速率（不推荐先做）**

- 需要拥塞控制钩子（仍要换分支），还要在管理端加「上行/下行带宽」配置，
  两端协商
- 配错直接拥塞崩溃（比 CUBIC 更糟），运维成本高
- 只有在用户能准确填写自己的带宽时才有意义

## 4. 不建议做的

| 想法 | 为什么不建议 |
|---|---|
| 应用层 FEC 前向纠错 | 丢包由 QUIC 判定并重传，应用层补包救不了拥塞窗口；额外带宽是纯浪费 |
| 增加 QUIC 流控窗口 | 当前已 4MB/16MB/8MB/64MB，远大于 BDP，不是瓶颈 |
| 增大批处理上限（64KB→更大） | 单流下只会加剧队头阻塞 |
| 无脑开 8/16 条流 | 弱网下调度与头部开销反噬 |

---

## 5. 验收方法

每一期都要有可对比的数字，否则无法判断收益：

1. **基准测速**：`speedtest` 或 `curl -o /dev/null` 拉一个大文件，记录 Mbps
2. **RTT 与丢包**：`ping 1.1.1.1 -n 100` 记 min/avg/丢包率
3. **隧道内部指标**：`/api/state` 的 `tunnel_quality`、`inner_bad`、`quic_lost`
4. **节点侧**：`流隧道流量` 的 frames/rx/tx/bad_pkt

判定口径：同一节点、同一时段、连续三次取中位数。

---

## 6. 建议顺序

1. **先做一期**（半天到一天），量出 socket 缓冲放大后的实际带宽
2. 如果还是远低于链路带宽，**做二期多流**
3. 只有前两期都到位、仍不满意时，才动**三期换 BBR**

理由：一期可能直接把问题解决（如果瓶颈确实是 socket 缓冲），
成本最低且不引入任何协议变更。---

## 7. 附录：当前实现有多路复用吗（2026-11-10 核对）

**没有。** 只有「一个设备一条流」。

| 位置 | 事实 |
|---|---|
| `vpnclient/ui.go:1015` / `main.go:416` | `openTunnelStream` 每次连接只调用一次，一条 `POST /tunnel` 流承载该设备的全部 IP 包 |
| `masque/node/stream.go:171` | `serveStream` 按设备 IP 注册一个 session |
| `masque/node/server.go:244` | `register()` 以 IP 为 key，**同 IP 新流会「接管」旧流**（`CloseWithError(0,"session replaced")`），不并存 |
| `main.go:517` / `server.go:125` | QUIC DATAGRAM 仍开启，但只服务于旧的组网/管理通道，数据面不走它 |

也就是说：QUIC 协议本身多路复用，我们只用了其中一条流；
设备之间是并发的（各自一条流），设备内部所有流量挤在一条流上。

### 二期必须同时改的一处（否则多流立刻互相踢掉）

`masque/node/server.go:244` 的 `register` 现在是：

```go
if cur, ok := s.sessions[sess.ip.String()]; ok {
    cur.conn.CloseWithError(0, "session replaced")   // 同 IP 直接踢掉旧流
}
s.sessions[sess.ip.String()] = sess
```

多流分片后同一设备会有 N 条流，这个「同 IP 接管」策略会把前面 N-1 条全踢掉。
二期需要同步改成 `map[ip][]*session`（或 key 用 `ip/shard`），
并把 `unregister`、`lookup`、`tunLoop` 的下发逻辑一并改成「按 shard 选流」。
