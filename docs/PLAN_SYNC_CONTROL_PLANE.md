# 方案：内网传输的同步与控制架构（Sync & Control Plane）

> 状态：**设计稿，待确认**
> 目标版本：V25.0 / Agent 1.9.0
> 关联：[PLAN_INTERNAL_NETWORK.md](./PLAN_INTERNAL_NETWORK.md)（内网直连基础方案）

---

## 一、为什么需要重新设计

当前实现是"能跑"，但不是"好架构"：

| 现状问题 | 后果 |
|---|---|
| 三条独立通道（WS 指标、HTTP poll、shell WS） | 状态分散，故障时各自重连，难统一控制 |
| 指标只发最新样本 | 断线期间的样本直接丢失，历史有缺口 |
| 任务靠 poll 领取 | 下发延迟取决于 poll 周期（现 60s） |
| 无 ACK 机制 | 任务是否执行只能靠超时判断 |
| 无背压 | 网络抖动时队列堆积或整包丢弃 |
| 无会话恢复 | 每次重连都 full sync，开销大 |
| 配置下发是"一次性推送" | 不知道节点是否真的应用成功 |

本次设计把内网通道升级为**统一的同步与控制平面**。

---

## 二、设计目标

1. **一条连接**：控制、任务、指标、统计全部复用单条 WSS
2. **不丢关键数据**：控制/任务可靠投递（ACK + 重发），指标有损但可补
3. **断线可续**：5 分钟内重连可恢复会话，补发未确认帧
4. **状态可对账**：desired vs actual，持续 reconcile
5. **有优先级**：控制 > 任务 > 指标 > 统计，拥塞时先牺牲低优先级
6. **内网优先**：内网为主，公网兜底，切换不断会话

## 四、传输层：单连接多路复用

### 4.1 帧格式

```
┌────────┬────────┬────────┬──────────┬──────────────┐
│ len(2) │ type(1)│ lane(1)│ seq(4)   │ payload(N)   │
└────────┴────────┴────────┴──────────┴──────────────┘
  大端长度  帧类型   通道号   单调递增    JSON / CBOR
```

| type | 含义 |
|---|---|
| `0x01` | HELLO / HELLO_ACK（会话建立、恢复） |
| `0x02` | PING / PONG |
| `0x03` | DATA（承载各 lane 的业务帧） |
| `0x04` | ACK（确认某 seq） |
| `0x05` | NACK（请求补发 from_seq） |
| `0x06` | FLOW（流控窗口调整） |

### 4.2 四条 Lane

| Lane | 内容 | 可靠性 | 拥塞策略 |
|---|---|---|---|
| **CONTROL (0)** | 端点切换、会话恢复、配置 patch、shell 会话 | 可靠（ACK+重发） | 阻塞写，必要时暂停 METRIC |
| **TASK (1)** | 命令下发、任务结果、执行 ACK | 可靠 | 同上 |
| **METRIC (2)** | CPU/内存/网络样本（2s） | 有损 | 队列满丢最旧 |
| **STATS (3)** | sing-box 统计快照（30s） | 幂等 upsert | 延迟发送 |

优先级仲裁：CONTROL > TASK > STATS > METRIC。
拥塞检测：发送队列 > 阈值 → 先降 METRIC 频率（2s → 5s → 10s），仍拥塞则丢 METRIC，CONTROL/TASK 永不丢。

## 五、同步模型

### 5.1 指标：滑动窗口 + 断线补传

```
Agent 本地环形缓冲（最近 60 个样本 ≈ 2 分钟）
  ├ 在线：每 2 秒发送 1 个
  └ 断线：继续累积到缓冲
       └ 重连后：一次性打包补传（CBOR 压缩，最多 60 条）
```

服务端按 `(server_id, sampled_at)` 去重 upsert，天然幂等。

**收益**：断线 2 分钟内的曲线不断档；不需要重传全部历史。

### 5.2 配置：声明式对账（Desired vs Actual）

```
面板 Desired:  { config_hash: "ab12", version: 7 }
Agent Actual:  { config_hash: "ab12", version: 7 }   → 一致，什么都不做

若不一致：
  面板 → PATCH { version: 8, files: [...], hash: "cd34" }
  Agent → 应用 → 回报 ACTUAL { version: 8, hash: "cd34" }
  面板 → 校验通过，标记 reconciled
```

关键点：

- 每 30 秒比对一次 hash（不必每次全量拉配置）
- 应用失败 → 回报 `error`，面板进入重试（指数退避，最多 5 次）
- 配置有版本号，忽略过期 patch（防止乱序）

### 5.3 统计：版本化快照

```json
{ "node_id": 5, "sampled_at": 1794000000000, "seq": 42,
  "conn": 17, "up": 123, "down": 456 }
```

`node_id + sampled_at` 作为唯一键，重复投递无副作用。

## 六、控制模型

### 6.1 任务状态机

```
pending ──deliver──▶ delivered ──ack──▶ acked
   │                    │
   │                    └─timeout(30s)─▶ retry(≤3) ─▶ failed
   └─expires_at 过期 ─▶ expired
```

- **幂等键**：任务创建时生成 `task_uuid`，Agent 侧记录已执行集合（5 分钟窗口），重复下发直接回 ACK
- **超时重发**：服务端 30 秒未收到 ACK → 重发（同 task_uuid），最多 3 次
- **结果回报**：`ack(task_uuid, ok, exit_code, output_hash)`

### 6.2 交互式终端

```
浏览器 ──WS──▶ 面板 ──CONTROL lane──▶ Agent
                    ◀──DATA(PTY 字节流)──

会话生命周期：
  open(session_id) → ready → data* → close
  断线：Agent 保留 PTY 30 秒，重连带同一 session_id 可续
```

### 6.3 端点切换（内网优先）

```json
{ "lane": 0, "type": "endpoint",
  "internal": "http://100.96.0.18:8080",
  "external": "https://agent.yangzifun.org" }
```

Agent 收到后：

1. 探测 `internal` 的 `/healthz`（3 秒超时）
2. 可用 → 用**同一 session_id** 在新地址重建连接（服务端保留上下文，无数据丢失）
3. 不可用 → 保持 external，60 秒后重试

## 七、会话与恢复

### 7.1 握手

```
Agent → HELLO { session_id?, last_recv_seq, agent_version, platform }
面板  → HELLO_ACK { session_id, server_seq, resume: true|false, window: 64 }
```

- `session_id` 为空 → 新会话（full sync）
- 携带且服务端未过期（5 分钟）→ `resume: true`，从 `last_recv_seq + 1` 补发
- 过期 → `resume: false`，Agent 做一次全量对账

### 7.2 补发

服务端为每条可靠 lane 保留最近 200 帧。收到 NACK 或 resume 请求时按 seq 区间重放。

## 八、背压与流控

| 机制 | 说明 |
|---|---|
| 窗口 | 每 lane 独立窗口，默认 64 帧，接收方通过 FLOW 帧调整 |
| 队列上限 | CONTROL 512 / TASK 256 / METRIC 64 / STATS 16 |
| 降级 | METRIC 队列 > 80% → 采样降频；> 100% → 丢最旧 |
| 熔断 | 连续 3 次写超时 → 关闭连接，走重连 + resume |

---

## 九、安全

1. 内网监听仅绑定 WARP 网卡（`100.96.0.18:8080`）
2. 防火墙仅允许 `100.64.0.0/10` 访问该端口
3. 握手仍校验 `ag_` 接入令牌（沿用现有机制）
4. 内网走 WireGuard 加密，明文 HTTP 不额外暴露
5. 公网 443 仅作兜底，可随时关闭

## 十、可观测性

面板新增「通道健康」视图：

| 指标 | 说明 |
|---|---|
| `transport` | internal / external |
| `rtt_ms` | PING 往返 |
| `queue_depth` | 各 lane 队列深度 |
| `drop_rate` | METRIC 丢弃比例 |
| `last_seq_gap` | 是否出现序号空洞（数据完整性） |
| `session_age` | 会话持续时间 |

异常规则：`queue_depth` 持续 > 80% 或 `drop_rate` > 10% → 提示节点网络质量差。

## 十一、实施阶段

| 阶段 | 内容 | 工作量 |
|---|---|---|
| **P0** | 帧协议 + 单连接多路复用（保留旧通道兼容） | 1.5 天 |
| **P1** | 指标滑动窗口 + 断线补传 | 1 天 |
| **P2** | 任务 ACK + 幂等 + 超时重发 | 1 天 |
| **P3** | 配置对账（hash diff） | 1 天 |
| **P4** | 内网端点切换 + 兜底探测 | 0.5 天 |
| **P5** | 背压、流控、观测面板 | 1 天 |
| **合计** | | **约 6 天** |

可分 3 轮交付：P0–P1（传输+同步）→ P2–P3（控制+对账）→ P4–P5（切换+观测）。

## 十二、兼容与迁移

| 版本 | 行为 |
|---|---|
| 旧 Agent (<1.9.0) | 继续走 HTTP poll + 简单 WS，不受影响 |
| 新 Agent (≥1.9.0) | 优先新协议；服务端 HELLO 不识别 → 回落旧路径 |
| 灰度 | 按服务器 ID 白名单开启新协议 |
| 回滚 | `app_settings.agent_protocol = legacy` 即刻全局回落 |

## 十三、与"基础内网方案"的差异

| 维度 | 基础方案 | 本方案 |
|---|---|---|
| 连接 | WS + HTTP poll 并存 | 单连接多路复用 |
| 指标 | 实时丢旧 | 滑动窗口 + 补传 |
| 任务 | poll 领取 | 推送 + ACK + 重发 |
| 配置 | 一次性推送 | 声明式对账 |
| 断线 | 重连后全量 | 5 分钟内续传 |
| 拥塞 | 无处理 | 分 lane 背压 |
| 观测 | 无 | 通道健康指标 |
